# 0002. 규칙은 skills 저장소 플러그인으로 배포한다 — 편집은 차단, Bash는 확인

- 상태: accepted
- 날짜: 2026-09-27
- 결정: JD

## 맥락

"main push 금지", "운영 DB는 조회만", "적용된 Liquibase changeset 수정 금지" 같은 규칙이 문장으로만 있었다.
에이전트는 문장 지침을 놓칠 수 있고, GitHub 무료 플랜이라 서버 쪽 브랜치 보호·required check도 없다.
Claude Code hook은 지침과 달리 매번 결정적으로 실행된다.

## 결정

규칙을 4층으로 나눈다.

| 층 | 무엇 | 강도 |
|---|---|---|
| AGENTS.md | 매 세션 알아야 할 것 | 권고 |
| 스킬 | 가끔 필요한 긴 절차 (테스트 점검·변경기록·완료 QA) | 호출 시 |
| hook | 사고로 이어지는 행동 | 결정적 |
| CI | 사람·도구와 관계없는 최종 확인 | 빨간 X |

hook은 `sramchorok-dev/skills` 저장소 루트의 `gardenstep-team` 플러그인으로 배포하고, 각 레포
`.claude/settings.json`의 `enabledPlugins`로 자동 활성화한다. 정책은 다음과 같다.

- **편집 도구(Edit·Write) — 차단(deny):** 비밀값 파일, 운영 설정, `.claude/settings*.json`, 이미 dev에 있는 Liquibase changeset. 사유가 에이전트에게 전달되어 대안을 찾게 한다.
- **Bash — 차단하지 않고 확인(ask):** 보호 브랜치 push·force push, 머지, 워크플로 실행, DB 쓰기, 원격 서버 접속, 파괴적 삭제 등. 사람이 사유를 보고 승인한다.
- **PR 게이트:** `gh pr create` 때 변경기록·`## 검증`·테스트 점검이 준비되지 않았으면 확인을 요청한다.
- **알림:** 테스트 파일의 스멜(PostToolUse), 코드 변경에 테스트가 없을 때 한 번(Stop).

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| Bash도 deny | 정당한 작업(JD의 운영 점검, 승인된 SQL)까지 막혀 우회 습관이 생긴다. 사람이 판단할 기회를 남긴다 |
| 레포마다 `.claude/hooks/` 복사 | 5개 레포에 같은 스크립트가 흩어지고 버전이 어긋난다 |
| git pre-push hook만 | Claude가 아닌 경로도 막을 수 있지만 설치가 사람마다 달라지고, 편집 단계는 막지 못한다 |

## 결과

- 좋아지는 것: 규칙이 한 곳에서 버전 관리되고 레포를 열면 자동 적용된다.
- 감수하는 것: hook은 로컬 방어라 Claude를 거치지 않는 작업은 막지 못한다. CI와 "빨간 X면 머지 금지" 규칙이 함께 필요하다.
  공개 저장소라 쓰기 권한이 곧 팀원 머신의 코드 실행 권한이다 — 쓰기 권한은 JD만 갖고 CODEOWNERS로 관리한다.
  플러그인 변경 시 `plugin.json`의 `version`을 올려야 팀원 캐시가 갱신된다.
- 다시 볼 조건: GitHub Team 플랜으로 올려 브랜치 보호를 쓸 수 있게 될 때, 확인 프롬프트가 너무 잦다는 피드백이 반복될 때.
