# 프로젝트별 설계 선택

| 규모/위험 | 먼저 갖출 것 | 추가 검토 |
|---|---|---|
| 버릴 실험 | 짧은 요청/성공 기준, 실행 확인, 외부 부작용 범위 | 팀 운영 장치를 일괄 설치할 이유가 있는가 |
| 계속 쓸 팀 도구 | intent/spec/plan, 공용 규칙, 결정적 테스트, CI, 독립 리뷰 | 실제 사용자 경로, 자료 접근, 재현 가능한 eval |
| 고객·운영 서비스 | 위 항목 + 정확한 버전의 DEV 증거, 승인·배포 통제, 복구 | 개인/금융정보, 데이터 정책, 운영 자격·실행 환경 분리 |

## 세 층

AGENTS/CLAUDE는 첫날 필요한 명령·경계·핵심 맥락만 유지한다. 반복 절차는 버전 관리되는 Skill로, 결정적으로 막을 규칙은 hook/lint/tests/CI로 옮긴다.
팀원이 같은 커밋의 규칙을 실제로 로드하는지 확인한다. 설정 파일에 SHA 문자열이 있다는 사실만으로 실행 버전이 고정됐다고 판단하지 않는다.

## 기록과 출처

한 제품의 변경은 제품 repo 안, 여러 제품에 걸친 변경은 공용 private 기록 repo를 고려한다.
각 산출물의 정본을 하나 정하고 Issue·원자료·PR·증거를 링크한다. 공개 하네스에 고객 원문이나 사내 위치를 넣지 않는다.
원자료 충돌은 담당자가 확정한 spec으로 해결한다. 가장 최근 메시지라는 이유만으로 기존 요구사항을 자동 교체하지 않는다.
API revision이 없으면 조회시각+내용 hash를 관측본으로 기록한다. 이것을 공급자의 원본 revision이라고 부르지 않는다.

## 예산과 기술적 강제

실제 구독에서 보호 설정 API/관리 화면을 읽어 지원 범위를 확인한다. 제품 이름이나 유료 등급만으로 private 보호 기능을 추측하지 않는다.
지원되면 native 보호 기능을 사용한다. 지원되지 않고 업그레이드를 원하지 않으면 다음 선택을 제시한다.
- GitHub 기록·CI·사람 수동 승인: 운영 부담이 가장 작다. 우회 실행을 기술적으로 막는 보장은 없다. 사용자가 이 수준을 목표로 선택했다면 기록·실제 CI·사람 승인 절차를 확인해 완료할 수 있다.
- 공용 승인/검증 서비스와 제한된 실행 자격: 구현·운영 비용, 장애·복구, 사람 등록 부담을 산정한다.
- 통제가 불완전한 전환 준비 단계: 문서와 CI를 진행하되 기술적 강제 미완료로 표시한다.

별도 서비스는 원칙을 따르기 위한 필수 설치물이 아니다. 사용자가 '대체 승인'을 선택했다는 말만으로 새 서버·패스키 운영까지 승인했다고 해석하지 않는다.
무엇을 막아야 하는지, 기존 수동 방식이 왜 부족한지, 누가 운영하고 각 팀원이 무엇을 등록해야 하는지 설명하고 구체적 설계로 선택받는다.
위 세 번째 상태는 강한 통제를 목표로 선택했는데 아직 구현하지 못했을 때에만 해당한다. 간단한 방식을 합의한 팀을 영구 미완료로 분류하지 않는다.

공용 서비스의 계약은 사람 신원과 승인 대상 버전, 승인 무효화, 신뢰된 필수 검사 목록, 원시 증거 출처, 변경 대상 비교, 재시도/결과불명 복구를 포함한다.
검사 후보가 자기 정책을 완화하거나 가짜 성공 파일을 만들 수 없도록 실행 경계를 나눈다.
승인 서비스 자체의 업그레이드는 별도 관리 경로로 다룬다. 코딩 에이전트가 서비스 호스트의 관리자 자격을 가지면 강한 운영 경계라고 주장할 수 없다.
훅만 설치하거나 로컬 JSON에 approved를 쓰는 것은 이 계약의 구현이 아니다.

## tests / evals

결정적 계약은 tests, 도구 선택·답변 품질·공격 대응은 evals로 검증한다.
제품 모델 평가와 코딩 하네스 평가를 별도 관리한다. 각 결과는 앱·모델·프롬프트·judge·하네스 버전과 입력 hash를 갖춘다.
외부 judge 전송 데이터와 비용을 먼저 정한다. 튜닝과 보류 입력을 구분하고 빈/skip 결과를 성공으로 세지 않는다.
커버리지·반복 횟수·성공률은 실제 위험과 기준선에서 정한다. 특정 사례의 숫자를 보편적인 필수 기준으로 복사하지 않는다.
