# 빠진 결정만 묻는 인터뷰

대화의 원문과 정정을 먼저 결정표로 정리한다. 각 항목에 확정/제안/미확인과 근거를 붙인다.
이미 확정된 답을 질문 목록으로 다시 보내지 않는다. 한 번에 1~3개의 서로 연결된 질문만 묻고 추천안의 이유를 짧게 붙인다.

| 결정 | 확인할 내용 |
|---|---|
| 목적/범위 | 해결할 가장 큰 문제, 새 프로젝트/전환, 저장소, 사용자, 제외할 작업 |
| 위험/검증 | 버릴 실험·팀 도구·운영 서비스, 돈/개인정보/외부 부작용, 실패 시 영향 |
| 사람 | 실제 계정, 동등 권한 또는 역할별 권한, 담당자/인계, 누가 요구사항·위험·운영을 결정하는가 |
| 리뷰 | 사람 상호 리뷰 필수/선택, 에이전트 별도 세션, 같은/다른 모델, 반복 상한 |
| 도구/정본 | Claude/Codex 등, 개인 PC와 공용 환경, 한 제품 또는 다중 repo 기록 위치 |
| 자료 | 메신저·디자인·파일·문서 위치와 허용 범위, 개인 DM 제외 여부, 쓰기/발신 별도 권한 |
| 비용/통제 | 현재 구독, 추가 비용 상한, native 보호 기능 사용 가능 여부, 운영 자격 격리 가능 여부 |
| 전환 | 계획 승인, 샘플 dry run, 시범 운영 필요 여부, 진행 중 PR, 전환 순서/복구 |
| 운영 | 수동 시작/자동 감시, 운영 승인 시점, 증거 보존·알림 데이터 정책 |

결정에 사람 승인과 에이전트 실행을 분리한다. 두 사람이 동등하고 상호 리뷰가 선택이면 담당자 한 명이 본인 작업을 승인할 수 있다.
이것은 작성 에이전트가 자기 코드를 독립 승인한다는 뜻이 아니다.
승인 대상과 내용이 같은 경우 이전 명시적 승인은 계속 유효하다. 새로운 유료 서비스 구매나 범위 밖 시스템 변경으로 확대하지 않는다.
