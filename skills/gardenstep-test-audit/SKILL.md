# Gardenstep 테스트 점검

바뀐 코드에 **규칙이 요구하는 테스트가 함께 왔는가**, 그 테스트가 **구현이 틀리면 실제로 떨어지는가**를 판정한다. 결과는 고정 양식의 영수증이다. 정책 정본은 [references/testing-policy.md](references/testing-policy.md)이며, 판정 근거는 항상 그 문서의 조항이다.

**규칙의 글자를 어기는 것은 규칙의 취지를 어기는 것이다.** "취지는 지켰다"는 통과 사유가 아니다.

## 언제 쓰나 / 언제 아닌가

- 쓴다: PR 열기 전 자기 점검, 주니어 PR 리뷰의 첫 단계, "테스트 있어?"라는 질문, CI `test-gate` 실패 원인 해석.
- 안 쓴다: 테스트를 **실행**해 통과 수를 확인하는 일(`chorok-completion-qa`), 리뷰 코멘트 말투 다듬기(`chorok-code-review`, `review-like-me`), 테스트를 대신 써 주는 일(요청받으면 판정 후 별도 작업으로).

## 실행 순서

### 1. 대상 확정

- 레포 디렉터리로 들어간다. `chorok/` 루트는 git 레포가 아니다.
- base는 PR의 base(보통 `origin/dev`), head는 PR 브랜치. `git fetch origin dev` 후 `git diff --name-status origin/dev...HEAD`가 비어 있지 않은지 본다.
- PR 본문이 있으면 파일로 저장한다(`gh pr view <n> --json body -q .body > /tmp/pr-body.md`).

### 2. 스크립트 실행 — 영수증 초안

`SKILL_DIR`은 이 `SKILL.md`가 있는 디렉터리다.

```bash
python3 "$SKILL_DIR/scripts/audit_tests.py" --repo . --base origin/dev --pr-body /tmp/pr-body.md
```

- 출력이 곧 영수증 초안이다: 변경 분류 → 필수 테스트 규칙(✅/❌/⚠️) → 스멜(파일:줄·규칙·고치는 법) → PR 본문 → 판정.
- 종료 코드 1 = FAIL. `--json`은 기계 판독용, `--exempt "<사유>"`는 `test-exempt` 라벨과 같은 효과.

상황에 따라 모드를 고른다. PR이 아니어도 된다.

| 상황 | 명령 | 판정 범위 |
|---|---|---|
| PR·브랜치 (커밋됨) | `--base origin/dev` (필요하면 `--head <ref>`) | 필수 규칙 + 스멜 + PR 본문 |
| 커밋 전 작업 트리 (PR 열기 전 자기 점검) | `--base origin/dev --working-tree` | 같음. 미추적 새 파일도 포함 |
| 특정 파일 몇 개만 | `--changed-files list.txt` (`A path` / `M path` 한 줄씩) | 같음 (git 불필요) |
| 레포의 기존 테스트 전부 (부채 조사·온보딩) | `--all-tests` | 스멜만. 변경↔테스트 매핑은 diff에서만 의미가 있다 |
- 스크립트가 보는 규칙의 목록과 예시는 [references/smell-catalog.md](references/smell-catalog.md), 레포별 경로·명령은 [references/repo-commands.md](references/repo-commands.md).

### 3. 스크립트가 못 보는 것 — 사람 눈 6가지

변경된 테스트 파일을 **직접 읽고** 아래를 확인한다. 각 항목에 근거(파일:줄)를 남긴다.

| 확인 | 통과 기준 |
|---|---|
| 제목이 동작인가 | 제목만 읽고 무엇이 깨졌는지 안다 |
| 기대값 출처 | 스펙·기획서·손계산. 구현을 돌려 나온 값 붙여넣기 아님 |
| 실패 경로가 진짜인가 | 실패 케이스가 실패 UI/4xx 응답을 단언한다 |
| mock 경계 | mock은 PG·S3·SES·LLM·외부 API만. 우리 코드끼리 mock이면 통합으로 |
| 뮤테이션 증거 | 영수증에 "무엇을 망가뜨리니 어떤 테스트가 떨어졌다" 한 줄 |
| 레포 간 계약 | 상태·이벤트명·DTO 필드 변경이면 상대 레포 테스트·PR 링크·배포 순서 |

결제·환불·금액·재고·권한·스키마 변경이면 실패·경합·멱등 케이스와 리드 승인 필요를 추가로 확인한다.

### 4. 판정

- **FAIL**: ❌가 하나라도 있거나 3단계에서 기대값 출처·실패 경로·mock 경계가 무너졌다. 리뷰를 시작하지 않는다.
- **WARN**: ❌는 없고 ⚠️만 있다. 각 ⚠️에 "확인함 — 사유" 또는 "고쳐야 함"을 단다.
- **PASS**: 둘 다 없다.
- 면제는 정책 §6의 절차(`test-exempt` 라벨 + 영수증 면제 줄 + 리드 승인)를 갖췄을 때만 인정한다. 절차 없는 "이번만"은 FAIL이다.

### 5. 보고

스크립트 출력 뒤에 아래를 붙인다. 주니어에게 전달하는 문구는 `chorok-code-review` 톤(질문형·왜를 설명·존댓말)으로 쓴다.

```markdown
### 사람 눈 확인
| 확인 | 결과 | 근거 |
|---|---|---|
| 제목이 동작인가 | ✅/❌ | `파일:줄` |
| … | | |

### 최종 판정: PASS | WARN | FAIL
- 고칠 것 (FAIL): <파일:줄 — 무엇을 — 어떻게, 정책 §n>
- 확인할 것 (WARN): <항목 — 리뷰어 판단 근거>
- 주니어에게: <2~4문장. 왜 이 테스트가 필요한지 한 줄, 고치는 방향 한 줄>
```

## 합리화 표

| 들리는 말 | 실제 |
|---|---|
| "테스트가 이미 많다" | 게이트는 **바뀐 동작**에 붙는다. 다른 테스트 수는 무관 |
| "UI만 바꿨다" | 사용자에게 보이는 변경이 곧 E2E 대상이다. 문구·스타일만이면 면제 절차를 밟는다 |
| "Mockito 테스트 넣었다" | mock 호출 검증은 결과를 증명하지 않는다. 값 단언 또는 통합 테스트가 필요하다 |
| "CI가 초록이다" | 초록은 실행 증거다. 정책 충족(실패 경로·영수증·뮤테이션)은 별개다 |
| "급하다, 나중에 붙이겠다" | 핫픽스 절차(24시간 내 테스트 PR)가 있다. 절차 없는 나중은 오지 않는다 |
| "로컬에서 눌러봤다" | 재현 불가한 증거는 증거가 아니다. spec으로 남긴다 |
| "AI가 테스트를 만들어 줬다" | 그래서 뮤테이션 확인이 필수다. 통과하는 테스트와 지키는 테스트는 다르다 |
| "이 정도는 WARN으로 하자" | 수준은 정책 표가 정한다. 판정자가 내리지 않는다 |

## 빨간 신호 — 멈추고 정책을 다시 읽는다

- 스크립트를 돌리지 않고 diff만 보고 판정하려 한다.
- 변경된 테스트 파일을 열지 않고 "테스트 있음"으로 넘어간다.
- 영수증 양식을 바꾸거나 항목을 뺀다.
- FAIL을 WARN으로 내리면서 이유가 정책 조항이 아니다.
- 결제·금액·재고 변경인데 실패·경합 케이스를 묻지 않았다.

## 하지 않는 것

- 테스트를 실행해 통과 수를 세지 않는다 — `chorok-completion-qa`.
- 요청 없이 테스트 파일을 고치지 않는다. 판정과 고치는 법까지만.
- 정책 문서를 판정 중에 고치지 않는다. 규칙이 틀렸다고 판단되면 판정은 현행대로 하고 개정 제안을 따로 남긴다.

## 도입 자산
