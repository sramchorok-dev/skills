# 판정이 애매할 때

시트의 판정 정의(`00 먼저읽기`·QA 운영 가이드)가 정본이다.

| 결과 | 뜻 |
|---|---|
| PASS | 그 환경·파라미터에서 합격 기준을 모두 확인했고 증거가 있다 |
| FAIL | 선행조건은 갖췄는데 제품 동작이 기준과 다르다 |
| BLOCKED | 데이터·키·계정·외부 승인·도구가 없어 실행하거나 확인하지 못했다 |
| NOT_RUN | 아직 실행하지 않았다. 테스트 파일이 있거나 예전에 통과했다는 이유로 PASS로 적지 않는다 |
| N/A | 이번 회차 범위가 아니다. **사람이** 정하고 사유와 판단자를 남긴다 |

집계에서 FAIL·BLOCKED·NOT_RUN은 분모에서 빠지지 않는다. 그래서 애매한 것을 PASS로 올리면 출시 판단이
틀어진다. 애매하면 낮은 쪽(BLOCKED·FAIL)으로 적고 이유를 남기는 편이 안전하다.

## 자주 만나는 상황

### 1. 기준 문구와 화면이 아주 조금 다르다
예: 기준 "상담이 접수 되었습니다!", 화면 "상담이 접수되었습니다!" → **불일치**. observed에 화면 문구를
그대로 적는다. 띄어쓰기 하나여도 기준은 기준이다. 기준이 틀렸다고 생각되면 `note`에 "TC 갱신 필요?"를
적어 사람이 판단하게 한다.

### 2. 기준이 최근 결정보다 오래됐다
예: G-03 기준은 "/estimate 4단계"인데, 10/9 결정으로 견적이 "새 랜딩 → 예전 단계"로 바뀌었다.
→ 기준대로 실행하고 기준대로 판정한다(대개 FAIL). `note`에 "TC 갱신 필요? 근거: <결정·PR>"를 적는다.
기대값을 제품에 맞춰 스스로 바꾸지 않는다. TC 버전을 올리는 건 사람이 한다.

### 3. 기준과 Figma가 다르다
기준(01 탭)이 판정 기준이다. Figma와 다르다는 사실은 `note`에 적는다(노드 번호를 알면 함께).

### 4. 선행 TC가 FAIL이라 진행할 수 없다
예: P-05 결제가 실패해 P-22를 할 수 없다 → P-22는 **BLOCKED**(blocked_reason: "선행 P-05 FAIL, Run …").
FAIL이 아니다 — P-22 자체 동작은 보지 못했다.

### 5. DEV 데이터가 없어서 화면이 비어 있다
예: 견적 기반 공사 선택 목록이 비어 있다. 기준이 그 목록을 요구하면 **BLOCKED**(데이터 없음)로 두고,
"DEV 데이터 준비 필요"를 보고에 적는다. 운영에도 데이터가 없는 게 확인된 경우만 FAIL 후보다 — 그 판단은 사람에게 넘긴다.

### 6. 외부 연동(실결제·알림톡 수신·실기기·실 OAuth)
DEV에서 확인할 수 없는 항목은 그 항목만 `확인불가`(사유 포함)로 적는다. 나머지 항목은 평소처럼 본다.
결과는 BLOCKED가 되고, 확인 못 한 항목이 무엇인지 남는다.

### 7. 클릭했는데 아무 일도 없다
하이드레이션 전일 수 있다([browser.md](browser.md)). 기다렸다가 한 번 더 해 보고, 그래도 안 되면 불일치.
observed에 "두 번 클릭, N초 대기 후에도 이동 없음"처럼 적는다.

### 8. 오류가 났지만 재시도하니 됐다
첫 시도의 실패도 결과다. **불일치**로 적고 observed에 "1차: <오류 문구>, 2차: 성공"을 쓴다.
간헐 오류는 재현 횟수(예: 5회 중 1회)를 남기면 고치는 사람이 훨씬 빨리 찾는다.

### 9. 기준에 없는 이상한 점을 발견했다
판정에는 넣지 않는다(기준 밖이다). `note`에 적고, 보고의 "기준 밖 발견"에 모은다. 심하면 결함 초안을 따로 쓴다.

### 10. 같은 TC를 다시 시험한다(재시험)
새 Run ID로 새 행을 만든다. 예전 행을 고치거나 지우지 않는다. 고쳐진 이슈를 확인하는 거라면 `issue_id`에
그 이슈 ID를 넣는다. 04 탭 상태는 사람이 바꾸지만, 보고에 다음 상태를 제안한다.

| 이슈 지금 상태 | 재시험 결과 | 제안 |
|---|---|---|
| RETEST_PENDING | PASS | FIXED_DEV (기준을 고쳐 해소된 거면 CORRECTED) |
| RETEST_PENDING | FAIL | OPEN으로 되돌림 |
| FIXED_DEV·CORRECTED | FAIL | 재발 — 재오픈할지 새 이슈로 할지 사람이 정함 |

### 11. 한 화면에서만 문제가 보인다
예: 홈(`/`) 모바일에 하단 탭바가 없다. 판정은 TC 기준대로 한다(SKILL.md 3단계 4번). 같은 요소가 있어야 할
다른 화면 결과를 `note`에 함께 남기면, 의도된 예외인지 회귀인지 사람이 빨리 가를 수 있다.

### 12. 코드나 주석이 기준과 다르게 말한다
예: 코드 주석에 "기획 확정 4탭"이라고 적혀 있는데 기준은 5슬롯이다. 판정에도 note에도 근거로 쓰지 않는다.
주석은 옛 결정일 수 있어 사람을 잘못된 방향으로 이끈다. 기준과 DEV 화면만 비교한다.
